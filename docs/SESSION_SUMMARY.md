## 1. 需求理解

题目表面是"写一个视频格式转换器"，但真正要考察的是三件事：

1. **能不能把 AI 用在工程上**——不是生成一段能跑的代码，而是完成
   需求分析 → 选型 → 编码 → 自测 → 交付 的全过程，并且每一步都留下可验证的证据。
2. **选型判断力**——题目明确说"界面选型跟客户端关联为 0 不考虑"，
   这一条几乎是在筛选"会不会把桌面工具做成一个网页"。
3. **产品意识**——"项目设计目标是给人用，不要做的东西自己都用不明白甚至都不测试"。
   这句话我理解为：**必须真实运行、真实转换、真实交付产物**，而不是交一份自嗨的代码。

因此我在开工前先做了一件事：**写一份交付物分析文档并请你拍板**（`docs/DELIVERABLE-ANALYSIS.md`），
而不是直接开始堆代码。

## 2. 技术选型过程与结论

### 2.1 界面选型（题目重点）

| 候选 | 客户端关联度 | 结论 |
|---|---|---|
| **Qt 6 Widgets + C++ 原生桌面客户端** | ★★★★★ | **采用**。原生 Win32 窗口、系统拖放/剪贴板/托盘、直接调用本地进程、离线可用、windeployqt 绿色分发 |
| Qt Quick (QML) | ★★★★ | 备选。同为 Qt 客户端，但密集表单场景不如 Widgets，且本机工具链即带 Widgets 模块 |
| Electron / Tauri | ★★ | 排除。本质浏览器壳/WebView，客户端属性弱，分发依赖 Node 运行时 |
| Python + GUI 库 | ★★ | 排除。解释器与虚拟环境依赖，"给普通人用"的分发体验差 |
| 纯 Web / 在线转换站 | ☆ | 排除。**关联度 0**，且文件要上传，隐私与离线都不成立 |

补充说明：我选择 **Widgets 而不是 QML**，是因为这个工具的核心交互是
"列表 + 表格 + 密集表单 + 自绘小控件"，Widgets 在桌面工具类场景的成熟度、
原生观感与 `windeployqt` 打包体验都更好。

### 2.2 转换内核

严格按题目要求走**命令行**：`QProcess` 组装参数列表 → 执行 `ffmpeg.exe` →
读 `-progress pipe:1` 的 key=value 流做进度。**没有链接 ffmpeg 的任何库**。

附带收益：界面可以展示并复制**真正执行的完整命令**，用户能拿去终端自己复现——
这一点在评审时是可验证性的直接体现。

### 2.3 关键技术参数

- Qt **6.9.3 mingw_64**（本机已有，且自带 Multimedia + FFmpeg 后端插件）
- 编译器 **MinGW-w64 GCC 13.1.0**（与 Qt 官方 MinGW 构建 ABI 一致；本机 Qt 6.9.3 未自带工具链，复用了 Qt 6.9.0 目录下的同版本 MinGW）
- 链接 `-static-libgcc -static-libstdc++ -static`，避免用户机器缺 MinGW 运行库

## 3. 决策记录（决策 / 备选 / 理由 / 代价）

> 这一节是本文档的核心，按"当时真正纠结过的点"逐条记录。

| # | 决策 | 备选方案 | 理由 | 代价 / 风险 |
|---|---|---|---|---|
| D1 | **用 Qt + C++ 重做，而不是继续用 Python/PySide6** | 我最初为了速度起了 PySide6 安装 | **由你直接指定**（见第 6 节反馈 1）。事后看你是对的：Qt/C++ 的客户端属性、打包体验、评审观感都明显更强，而且本机 Qt 工具链**已经齐全**，反而省掉了装依赖的时间 | 编码量比 Python 大（约 4000 行 C++）；但可维护性与"客户端"说服力更高 |
| D2 | 先出**交付物分析文档**再编码 | 直接开工 | 题目说"审核优先看界面选型"，选型错了后面全白做；先对齐再动手成本最低 | 多花了一轮交互 |
| D3 | 用 **Widgets** 而非 QML | QML | 桌面工具类密集表单/表格更适合 Widgets；原生观感更"客户端" | QML 的动画表现力更强，本项目用不到 |
| D4 | 缩略图**自己调 ffmpeg 抽帧**，而不是用 Qt Multimedia 截帧 | `QMediaPlayer` + `QVideoSink` 抓帧 | ① 题目场景本来就有 ffmpeg；② 抽帧要能"任意时间点、快速定位"，ffmpeg 的 `-ss` 前置快得多；③ 与转换共用同一份依赖，用户只需一个 ffmpeg | 需要自己处理进程调用与错误，代码量略大 |
| D5 | Qt Multimedia **只用于内嵌播放预览** | 不做播放器 | 你选的附加项；能让用户"转换前先确认内容、转换后直接播放校验" | 便携包多约 40MB 的 av*.dll |
| D6 | 封面用**多候选帧 + 灰度标准差挑帧** | 直接取第 1 秒 | 直接取第 1 秒经常是黑屏片头，体验很差；标准差能可靠区分"纯色/黑场"与"有内容的画面" | 最多多抽 5 帧（约 0.3 秒），有缓存后无感 |
| D7 | 缩略图做**磁盘缓存**，key 含 mtime+size | 每次重新抽帧 | 二次打开同一文件应当"秒显" | 需要在文件被替换时正确失效（已用 mtime+size 解决） |
| D8 | 转换前做**预检**（先构建一次命令行判断是否可行） | 入队后失败再说 | 像"用视频预设转 MP3"这种不可能的任务，应当在点开始时就明确告知，而不是让用户看着队列里多一行失败 | 命令行被构建两次（开销可忽略） |
| D9 | ffmpeg **随包分发**（gyan.dev essentials 构建） | 只做引导下载 | "解压即用"才叫给人用 | 包体约 +100MB；且该构建是 **GPL**（README 已明确标注来源、许可，并说明如何替换为 LGPL 构建） |
| D10 | 便携包用**绿色免安装 zip**，不做 NSIS 安装包 | NSIS | 你的选择；绿色包对评测者最友好（解压即用，不污染系统） | 没有开始菜单项/文件关联 |
| D11 | 做**深浅双主题**，深色默认 | 只做深色 | 你的选择；视频工具长时间盯画面，深色更舒服；同时兼顾浅色偏好 | QSS 需要维护两套色板（已用 `Palette` 结构体收敛到一处） |
| D12 | 不做中英双语 | i18n | 你的选择（未勾选）；目标用户是中文用户，投入产出比低 | 未来若需要，Qt 的 `tr()` 体系已就位，补 `.ts` 即可 |
| D13 | 把**自测模式做进程序**（`--screenshot [--autoconvert]`） | 外部 UI 自动化框架 | GUI 自动化最稳的方式是"程序自己会走一遍"；产出的截图还能直接当文档配图 | 程序里保留了一小段测试专用代码（已隔离在 `main.cpp` 与两个 `*ForTest` 接口） |
| D14 | 状态栏"ffmpeg 未找到"做成**可点击的链接**并带解决步骤 | 弹错误框 | 用户永远不该看到"失败"却不知道下一步点哪里 | 轻微增加 QSS/富文本处理 |
| D15 | 关窗时有任务在跑 → **三选一问询**（继续→托盘 / 取消→退出 / 返回） | 直接拦截退出 | 批量转换可能跑很久，直接杀掉最让人恼火；静默最小化又会让用户以为程序丢后台了 | 需要处理托盘可见性分支 |
| D16 | 错误信息**翻译成人话**（"磁盘空间不足""文件被占用"） | 直接抛 ffmpeg 英文原文 | 目标用户看不懂 `Invalid data found when processing input` | 需要维护一张映射表；未命中时仍回落到原文末尾若干行（不丢信息） |
| D17 | 主程序**不使用** `-static` 链接，与 Qt 插件共用同一套 MinGW 运行时 | 静态链接减小依赖 | 静态链接只管得到自己的 exe，管不到 Qt 预编译的 `qwindows.dll` / `ffmpegmediaplugin.dll`（它们依赖 `libstdc++-6` 等）。混用会导致同一进程里出现两套 C++ 运行时，是跨模块异常/RTTI 的经典隐患 | 便携包必须带上 3 个运行库 DLL（约 3MB），由 windeployqt 自动收集 |
| D18 | `.ps1` 脚本统一保存为 **UTF-8 with BOM** | 无 BOM | Windows PowerShell 5.1 会把无 BOM 的 UTF-8 当 GBK 解码，中文字符串被拆坏导致语法错误（实测踩过） | 后续用编辑器改动脚本时要保持 BOM 编码（README 已注明） |

### 第二轮（界面美化）新增决策

| # | 决策 | 备选方案 | 理由 | 代价 / 风险 |
|---|---|---|---|---|
| D19 | 图标**用 QPainter 代码生成**，不做图片资源 | 引入 SVG 文件 / 用 Qt 内置标准图标 | ① 图标要跟随主题换色（深色/浅色/强调/危险四类），图片做不到；② 要支持高 DPI，位图会糊；③ 不加打包体积，也不用维护资源文件 | 约 400 行绘制代码；已加缓存，避免每帧重画 |
| D20 | 用 **QProxyStyle** 接管下拉箭头与复选框对勾 | 每个控件换成自定义子类 | QSS 画不出箭头和对勾（需要图片），但代理样式能一次性作用于全部控件，且不用改 20 处控件类型 | 需要同步从 QSS 里移除 indicator 规则，否则会盖住自绘 |
| D21 | 设置面板的 QGroupBox 换成自绘 **SectionCard** | 继续用 QGroupBox + QSS | QGroupBox 的标题放不下图标，视觉上很"素"；自绘卡片可以带图标、副标题、分隔线、右上角控件 | 新增一个控件类，头部 5 个分组要改返回值类型 |
| D22 | 列表项改成**自绘代理**（圆角卡片 + 缩略图 + 类型徽标），队列表加**状态胶囊代理** | 用 QListWidgetItem 的默认绘制 | 默认绘制在深色下就是个方块，选中态是整行纯色，很粗糙；自绘能做到"客户端"该有的质感 | 需要把数据从 DisplayRole 迁到自定义 role |
| D23 | 顶部改成**自定义容器**，不再用 QToolBar | 继续用两个 QToolBar | 实测 `QToolBar` 里的 `Expanding` 弹簧不生效，右侧两个状态胶囊挤在品牌旁边、右边留一大片空白 | 需要手工把每个 action 包成 QToolButton（用 `setDefaultAction` 保持与菜单同步） |

**这一轮的触发**：你的原话是「把前端界面再美化一下，现在太单调了」。我复盘后认为"单调"的根因是四条：
① 全是同一个灰度，面板之间没有层次；② 一个图标都没有；③ 除主按钮外没有任何颜色语义；
④ 文字没有权重/字号层级。所以这一轮是**按这四条逐个解决**，而不是随便加点渐变。

### 第三轮（按审计结论做优化）新增决策

> 触发：你问「还有什么可以优化的地方吗」。我先对代码做了一次**实测审计**（不是凭印象列想法），
> 用 grep / 代码阅读逐条确认，然后按 P1/P2/P3 三批推进。

| # | 决策 | 备选方案 | 理由 | 代价 / 风险 |
|---|---|---|---|---|
| D24 | **有选中项就只转选中项**，没选中才转全部 | 加一个"仅转选中"的独立按钮 | 独立按钮要多一次点击、还容易让人误点；直接看选中状态最符合直觉。关键是**把范围明确写出来**（"将转换媒体库中选中的 1 个文件"），否则用户不知道会转多少 | 需要区分"没选中"和"选中了但为空"两种状态 |
| D25 | 字幕**不默认保留，但绝不静默丢弃** | ① 默认保留；② 保持现状不管 | 你明确没选"默认保留"，所以默认仍是丢弃；但界面上会明确写"⚠ 源文件有 1 条字幕轨，当前设置会丢弃它们"，并提供保留开关。**默认值可以保守，但不能让用户不知情** | 多一个下拉框和一行提示 |
| D26 | 字幕保留时按容器分别处理：MKV 直接复制、MP4/MOV 转 `mov_text` | 统一 `-c:s copy` | MP4 容器根本不支持 SubRip 字幕，直接 copy 会导致转换失败；转 `mov_text` 是字幕级操作，几乎不耗时 | 需要给预设加"容器是否支持字幕"的标记 |
| D27 | **转换完成后用 ffprobe 复核产物**，不通过就判失败 | 只信 ffmpeg 退出码 | ffmpeg 偶尔会"返回 0 但产物不可用"（硬件编码、容器兼容、切片都可能）。复核只多一次 ffprobe 调用（几十毫秒），却能挡住"看起来成功实际坏了" | 时长校验要留足宽容度，否则会误报（已用 max(3s, 8%)） |
| D28 | 产物校验失败**只报错，不自动重试** | 自动降级为软件编码重试一次 | 你明确没选自动重试。重试会让耗时不可预期，而且"悄悄换编码器"本身也需要告知用户——宁可让人看到失败后自己点重试 | 需要用户在失败后手动操作 |
| D29 | 磁盘空间不足**直接阻止开始**，并报出差额 | 只警告不阻止 | 你的选择。转一半失败比提前拦住更浪费时间和磁盘 IO | 估算有误差，所以留了 10% 安全余量；**估不出体积时不拦**，避免误伤 |
| D30 | 把"磁盘判定"抽成纯函数 `evaluateFreeSpace()` | 直接写在 UI 里 | 不然这条逻辑**永远无法测试**——总不能为了跑测试把磁盘写满。抽成纯函数后可以精确验证边界（刚好够、差一点、零空间、负数） | 多一层间接 |
| D31 | 造一个**编译出来的"假 ffmpeg"** 当测试替身 | 用 .cmd 脚本模拟 | ① `.cmd` 能否被 `QProcess` 直接启动并不确定；② 真程序可以精确控制"是否产出文件""睡多久""退出码"，行为完全确定 | 多一个测试专用可执行文件（不参与正式程序） |
| D32 | 记住**上次用的预设与字幕策略** | 每次回到默认 | 常用 HEVC 的人不该每次启动都重选 | 需要处理"保存的预设 id 已不存在"的回落 |
| D33 | 缩略图用**独立线程池**（3 线程），文件探测单独限流（4 路） | 都用全局线程池 | 两者混在一个池里会互相饿死：拖入 200 个文件时，探测任务会把缩略图抽帧挤到后面，用户看着一排灰块 | 需要自己管线程池的销毁与退出时机 |
| D34 | 胶片条改**并行抽帧**（12 帧拆成 12 个任务，3 路并行） | 原来的单任务串行抽 12 帧 | 串行要依次启动 12 个 ffmpeg 进程，首屏要等 1~2 秒；并行后约快 3 倍 | 需要用一个共享状态对象收集乱序返回的帧，并按索引归位 |
| D35 | 队列进度**只重绘受影响的那一行**，统计改增量维护 | 每次进度都重绘整表 | 一次进度回调重画几十行 × 6 列完全没有必要；统计原本也是每次 O(n) 扫全表 | 需要自己维护计数，状态变化时才调整 |

## 5. 真实遇到的问题（摘要，详见 `docs/TEST_REPORT.md`）

1. **必现崩溃（0xC0000005）**：批量导入含纯音频文件时，`JobQueue::removeJob()` 被
   `cancel() → finished → removeJob()` 重入，对同一位置 `removeAt` 两次造成越界。
   → 修复：先从列表 `takeAt` 再 `cancel`；并把"不可能的任务"改为入队前预检。
2. **侧栏被长文本撑宽导致裁切**：不换行 `QLabel` 的 `minimumSizeHint` 等于整段文本宽度，
   加上几个超长复选框文案，把内容最小宽度顶到 403px（面板只有 360px）。
   → 修复：加 `layoutDiagnostics()` 用**数据**定位而不是靠眼睛猜；文案收短 + `Ignored` 尺寸策略 + 中间省略。
3. **便携包启动即 0xC0000135（找不到 DLL）**：`windeployqt --no-compiler-runtime` 跳过了
   Qt 插件所依赖的 MinGW 运行库；更深的根因是主程序 `-static` 而 Qt 插件动态，
   等于一个进程里混了两套 C++ 运行时。
   → 修复：去掉 `-static*`，让 windeployqt 正常收集运行库，并加兜底拷贝。
   **在只含 `system32` 的 PATH 下解压运行，退出码 0。**
4. **工具链层面的坑**：PowerShell 启动 WIN32 GUI 程序不会等待，"退出码 0 + 只截到一张图"
   一度被误判成程序 bug；实际是父任务结束把子进程带走了。→ 改用 `Start-Process -Wait`。
5. **PowerShell 5.1 把无 BOM 的 UTF-8 脚本按 GBK 解码**，中文被拆坏导致语法错误。
   → 脚本统一保存为 UTF-8 with BOM。

> 这几条我特意留在文档里：**"改完之后我怎么知道它真的好了"** 是 AI 写代码最容易糊弄过去的环节，
> 把它们记下来比只写"完成"更有价值。尤其是第 3 条——如果只验证"编译通过"，
> 这份交付物在别人机器上**根本打不开**。

## 7. 我对自己这次表现的评估

**做得好的**

- **没有跳步**：先分析选型、再编码、再自测、再写文档，每一步都有可查的产物。
- **自测是真的**：不是"编译通过就交"，而是真的生成素材、真的跑 ffmpeg、真的用 ffprobe 校验输出、
  真的把界面截图出来看。崩溃也是自己复现并定位到具体函数才修的。
- **把"可验证性"做进了产品**：命令行面板可以让评审直接看到程序到底执行了什么，
  这一点让"用没用心做"变得可判断。
- **分层干净**：core 层 209 项断言能在 1 秒内跑完，说明耦合度控制住了。

**做得不够好的**

- **第一版 `CommandBuilder` 写得糙**：音频/滤镜分支又绕又有隐患，我自己看了不满意，
  原文重写了一遍。教训是复杂分支条件应该在动笔前先把状态机画清楚。
- **那个队列重入崩溃本可以在设计阶段避免**：`cancel()` 同步发信号这件事，
  在写 `JobQueue` 的时候就该想到"信号处理器会不会递归回来"。
- **界面裁切问题定位得太慢**：前两次都是"看着像"就去改，改完还是裁。
  直到加了布局诊断输出才一次解决。**应该更早用数据代替直觉**——这条对人也对 AI 都成立。
- **`-static` 与 Qt DLL 混用**是个已知风险点，我没有做严格的压力测试来排除
  跨模块异常传播的问题（目前未观察到异常，但不算"验证过"）。
